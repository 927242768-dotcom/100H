# MNN 模型接入判断

## 结论

`D:\100H\r2_mobile` 下面这组文件已经不是 `pt` / `onnx`，也**不需要再做格式转换**：

- `b320_backbone_h.mnn`
- `b320_header_h.mnn`
- `b640x_backbone_h.mnn`
- `b640x_head_h.mnn`
- `litemodel_cls_96xh.mnn`
- `rpv3_mdict_160h.mnn`

它们对应的是一套**基于 MNN 的车牌检测 + 车牌识别 + 车牌类型分类**模型链，而不是通用 YOLO 检测模型。

## 模型角色

从文件名可以直接判断出这套模型分工：

1. `b320_backbone_h.mnn` + `b320_header_h.mnn`
   低分辨率车牌检测模型，输入等级偏快。
2. `b640x_backbone_h.mnn` + `b640x_head_h.mnn`
   高分辨率车牌检测模型，精度更高但更慢。
3. `rpv3_mdict_160h.mnn`
   车牌字符识别模型。
4. `litemodel_cls_96xh.mnn`
   车牌颜色 / 类型分类模型。

## 对当前项目的意义

这意味着：

1. 你现在手上的不是“还要转成 MNN 的训练文件”，而是**已经可用于 ARM 侧部署的推理模型**。
2. 但它们也不是“拿来就能直接塞进当前 Python 检测接口”的 YOLO 单模型。
3. 如果要真正跑起来，除了这些 `.mnn` 文件之外，还需要：
   - `MNN` 运行时
   - 一套和这些模型匹配的前后处理代码
   - 最好直接使用现成的 `HyperLPR` C++ SDK / Demo

## 推荐路线

推荐直接走：

1. ARM 侧继续保留当前 `摄像头 -> FPGA 预处理 -> HDMI 显示` 管线。
2. 车牌识别部分不要自己从零手写 MNN 后处理。
3. 直接在 RK3568 Linux 上编译并使用 `HyperLPR` 的 C++ 版本。
4. 把 `D:\100H\r2_mobile` 作为模型目录传到板子上。

这样做的原因：

1. 这套模型本来就是按“检测 + 透视矫正 + 识别 + 分类”的流水线设计的。
2. 其中检测模型不是单纯输出普通框，通常还会带角点 / 结构信息，方便车牌校正。
3. 车牌识别效果高度依赖这些配套前后处理，自己从零重写成本很高，也容易跑偏。

## 当前还缺什么

仅靠当前这 6 个 `.mnn` 文件，还**不够直接落板运行**。

还需要至少其一：

1. `HyperLPR` 官方 C++ SDK / Demo 源码
2. 已经编译好的 `HyperLPR` 动态库和头文件
3. 或者你自己板子上已经有可用的 `MNN Python` 绑定，并且愿意额外实现整套前后处理

其中最推荐的是第 1 条。

## 当前最稳的接入顺序

1. 先在 RK3568 板子上确认：
   - `g++`
   - `cmake`
   - `pkg-config`
   - `OpenCV`
   是否可用。
2. 准备 `MNN 2.0+` 和 `OpenCV 4.0+`。
3. 编译 `HyperLPR` 的 Linux C++ 版本。
4. 先单独跑一张图片，确认能输出车牌文本。
5. 再把它接回当前 `pipeline.py`，做实时显示。

## 和“YOLO”目标的关系

从赛题目标看，你后面未必一定要坚持“YOLO”这个名字。

如果你的核心任务是：

1. 车牌检测
2. 车牌字符识别
3. 结果显示到 HDMI

那么这套 `MNN + HyperLPR` 往往比“重新找一个 YOLO 再自己补 OCR”更直接。

## 建议

下一步优先做：

1. 先确认板子上能不能编 `HyperLPR C++`
2. 再决定是：
   - 直接用 HyperLPR 做整帧车牌识别
   - 还是让 FPGA 先给 ROI，再把 ROI 送给 HyperLPR 做精识别

第一版建议直接做“整帧识别”，先求通，再优化到“FPGA ROI + ARM 识别”。
